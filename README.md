# DSH Memory v0.1

A Host-only Cordis bundle for durable, sourced memories that the Agent can manage during ordinary work. Install the package directory in each desired DSH Profile with the DSH Plugin Manager; this repository does not install or activate itself.

## Data and scope

The plugin stores `$DSH_HOME/plugins/dsh-memory/memories.json`, using the installed `@deepseek-ai/dsh-home-paths` API. Profiles share Global entries only when they resolve the same DSH Home. Workspace entries use the canonical real path of the working directory (case-folded on Windows). Do not place the data file on a network volume shared by independent hosts: the installed file lock checks local PIDs only.

The plugin uses Session Query to verify historical user messages; it does not build a session index. Source verification replays `working-directory/change` events from the session header to the cited event, including inherited fork events. It rejects unavailable, deleted, or noncanonical historical directories rather than substituting the current directory. Global entries require an exact quote from the **same user message** explicitly stating cross-Workspace applicability. Exact-string checks establish provenance, not that a paraphrase is correct or that the user's words really imply a general rule.

## Autonomous use (default)

The Agent can save a compact, durable user preference, standing convention, or project fact when a direct human user message supports it. A clear correction can update an existing entry. It should skip transient task progress, easily rediscovered facts, speculation, secrets, and credentials. Source text from tools, files, web pages, or other agents is not a direct human user message. For uncertain meaning or scope, use the candidate review flow below or leave memory unchanged. These are Agent instructions; the plugin enforces the event, quote, scope, and revision checks but cannot independently judge the meaning of a proposed summary.

1. Use `memory_search` with words from the task to find relevant reviewed entries. It returns up to 5 by default (10 maximum), with matched terms, a short preview and an id; call `memory_read` to inspect full content and source. Search is lexical, read-only and runs only when called. Use `memory_list` to see all visible entries, including `needs-review` legacy entries, and obtain the exact `revision` required for a write.
2. Use `memory_add` with `content`, `scope`, `expected_revision`, `source_kind` and exact `source_quote`. `source_kind: user` cites a current direct user event; `source_kind: session` also needs `source_session_id` and `source_seq` for the historical user event. Supply `source_seq` when a current-session quote repeats. For Global memories add `global_scope_quote` from the **same** user message; project-specific facts belong to Workspace scope. A write that fails the source, scope or revision check changes nothing.
3. For a clear correction, find the single old entry and use `memory_update` with its id, a fresh exact revision, the new content and a **current-session** direct user message. When the old memory came from the same session, the cited correction event must be newer. The entry keeps its id, creation time and scope. If the correction or intended target is ambiguous, use `memory_propose` or leave it unchanged.
4. Use `memory_delete` for one clearly obsolete or incorrect memory. It hides the entry from list, search and Prompt, and archives it for 30 days. `memory_trash` shows restorable entries and their expiry. To restore, ask the user to send the direct message `恢复记忆 <完整 id>` or `Restore memory <full id>` and then call `memory_restore` with the exact id, that message as `source_quote`, and a fresh revision. A deletion is not a permanent erasure: the archive retains content and source during the recovery period. To erase on a user's request, ask them to send `永久遗忘记忆 <完整 id>` or `Forget memory <full id> permanently`; call `memory_forget` using that exact latest message as `source_quote` and a fresh revision. This erases the active or archived entry without a recovery path. These explicit commands are only for restore and permanent erasure; ordinary autonomous deletion needs no second user message.

Expired archives are excluded from `memory_trash` and cannot be restored. They are physically pruned on the next successful store mutation, not by a background timer. The archive holds at most 100 unexpired entries; further recoverable deletions fail until an archive is restored, expires, or is permanently forgotten.

## Optional write approval

`writeApproval` defaults to `false`; ordinary `memory_add`, `memory_update`, and `memory_delete` calls can commit without a second user message. Setting it to `true` blocks these direct tools and requires the existing `memory_propose` → `memory_decide` flow. It does not change the explicit user-requested `memory_restore` and `memory_forget` tools.

For an addition, propose `content` and `scope`. For a replacement, give the exact old `replace_id` and keep its scope. For deletion, give the exact old `delete_id`, `scope`, and no content; read and show the old entry before asking for approval. The deletion command includes a short preview, while the returned `replaces` entry contains the full old content. Show the proposal and, where relevant, the full old entry, then ask the user to send the returned `commands.confirm`, `commands.reject`, or `commands.revisePrefix` text as a **separate direct message**. A delete candidate can be confirmed or rejected, not revised. The next `memory_decide` call checks that exact new user event; Global addition/replacement confirmation also requires `适用于所有工作区` or `Applies across all workspaces` in that message. Candidates are visible only to the proposing session and their original Workspace, and do not enter search or Prompt. `memory_pending` lists them and returns the latest revision.

Candidate confirmation pins a replacement or deletion to the old entry's content and source. If it changes meanwhile, confirmation refuses to touch it. Candidates persist when the same session resumes, with at most 25 per session and 100 in the store. There is no timeout or automatic acceptance. Candidates are also available when `writeApproval` is off and the Agent wants a human decision.

## Prompt, recovery and compatibility

The plugin always adds a short policy to the Agent's system context: consider relevant prior memories during ordinary tasks and decide whether a direct human message merits a durable, sourced addition, correction or archive. It calls for autonomous writes in the default mode and proposal/decision in `writeApproval` mode. This policy contains no stored memory content. The **background entry injection** is disabled by default (`promptEntries: 0`); when enabled, it adds up to `promptEntries` reviewed entries within `promptCharacters` total characters (default 1200), labeled as background information. It still orders by verification time, not task relevance. Candidate, archived and legacy `needs-review` entries are excluded. There is no automatic summarization, semantic retrieval, conflict merging, threat scanner, or background reflection.

A new successful mutation writes version 4 of the JSON format, with `entries`, `candidates`, and `trash`. Earlier v1–v3 files remain readable until a write upgrades them. **Upgrade every Profile sharing one DSH Home before its first write with this plugin version:** an older plugin may refuse a v4 file. Legacy entries without recorded event-time Workspace are visible to `memory_list` as `needs-review`; they are excluded from search and Prompt until replaced with a newly sourced entry.

Malformed, unreadable, unknown-version or stale data cannot be overwritten through these tools. Writes use `withFileLock` around read, compare and atomic replacement; cooperative writers on one host serialize. Orphaned locks may require an operator to check for live writers. Atomic replacement does not `fsync`; abrupt power loss can lose the latest reported write. External writers bypassing this lock may race. Restore a known-good backup externally if the file is corrupt; list again before editing.

Tests use Node's test runner and create files only under the operating system's temporary directory: run `node --test test/*.test.js` from this repository. Tests do not install the plugin into a Profile or touch real memory data. To check integration, inspect the active Profile's Plugin Inventory and run read-only `memory_list` or `memory_search` in that Profile before testing writes with non-sensitive examples.
