# DSH Memory v0.1

A Host-only Cordis bundle for explicit, sourced facts useful in future sessions. Install the package directory into each desired DSH Profile with the DSH Plugin Manager. This repository does not modify or install into any Profile by itself.

## Data and scope

The plugin uses the installed `@deepseek-ai/dsh-home-paths` API to derive `$DSH_HOME/plugins/dsh-memory/memories.json`. Profiles on the same machine share Global entries **only if they resolve the same DSH Home**. Workspace entries are matched against the existing working directory's canonical real path; on Windows the canonical spelling is folded to lower case. Profile names are not part of the data key. Do not put the data file on a network volume shared by independent hosts: the installed lock checks PIDs on this host only.

The package directly depends on the DSH supplied home-paths and atomic-write libraries. It does not use Session Persistence for memory or index historical sessions. Active candidate decisions check direct `user/message` events from the calling session's event log; the S1 historical quotation verifier remains available in code but is not a direct write tool in S3. The verifier replays `working-directory/change` from the header through the cited user event, including inherited fork events. It refuses Workspace attribution when the earlier directory was never recorded, has disappeared, or is not a currently canonical path; it never substitutes the current default directory for a missing historical one. The Host bundle still declares Session Query as a dependency, so activation stays inactive if that service is unavailable. Optional FTS5 is not required.

Global means eligible in every Workspace of every Profile using the same DSH Home. It is appropriate only when the user explicitly states cross-Workspace applicability. An exact `global_scope_quote` from the cited message records that declaration; exact-string checking cannot establish its meaning. Review Global content before saving it. Existing Global entries without this declaration remain visible for explicit review but are excluded from Prompt injection.

## Usage

1. Call `memory_search` when the current task or the user asks for a stored fact, using descriptive terms from that task: for example `{"query":"Aurora deployment","limit":5}`. It returns at most 5 matches by default (maximum 10), each with an id, scope, verification time, matched terms, and a preview of at most 240 characters. `totalMatches` counts matching visible, reviewed entries. With no match it returns `{"totalMatches":0,"entries":[]}`. Search is read-only and runs only when called; it never changes the Prompt automatically.
2. Call `memory_read` with a result's exact id when its full content and source are needed. Use `memory_list` to inspect all visible entries, including `needs-review` entries, and to get the `revision` required for edits (50 per page by default; use `offset`, `limit`, and `nextOffset` to page).
3. To save a fact, call `memory_list` for the latest `revision`, then call `memory_propose` with `content` (1–2000 characters), `scope`, and `expected_revision`. To replace an existing fact, first use `memory_read`, show the old and proposed content to the user, and pass its **exact** id as `replace_id`; the old scope and Workspace are kept. Proposal only saves a pending candidate; it does not change search, list, or Prompt results. The result supplies the candidate id and exact `commands.confirm` / `commands.reject` / `commands.revisePrefix` to show the user. Use `memory_pending` to recover visible pending candidates and the current revision in the same session.
4. The user must send the **entire** confirm or reject command as a separate direct message; for example `确认记忆候选 <id>：<完整内容>` or `拒绝记忆候选 <id>`. To change a candidate, the user sends `修改记忆候选 <id>：<新完整内容>`; call `memory_decide` with `action: revise`, `new_content`, and the current `expected_revision`. The changed candidate remains pending and needs a **new** confirmation message. For a replacement, the confirmation command includes both the candidate id and the exact old id (`确认替换记忆候选 <id> 旧记忆 <old-id>：<完整内容>`). The result also provides English command variants when `language: en` is requested.
5. After the direct user message arrives, call `memory_decide` with the candidate id, `action: confirm` or `reject`, and the latest revision from `memory_pending` / `memory_list`. The plugin checks that this is a newer real user event in the **same session**, and, for Workspace memories, in the candidate Workspace at the time of that event. Confirmation stores that message as the fact's source. Global confirmation additionally requires `适用于所有工作区` (or `Applies across all workspaces`) on its own line in **that same user message**; a model cannot declare Global scope on the user's behalf. Rejection removes the candidate without changing a fact. Confirmation of a replacement updates the old entry in place, preserving its id and creation date; if the old entry changed or disappeared since proposal, the operation fails and leaves the candidate pending. `memory_delete` is an independent explicit deletion of a visible fact and still requires its exact current revision.

All decision commands are checked as whole user messages, so a casual “yes” is not confirmation. There is no timeout or automatic acceptance. Candidates stay in the shared store but are visible only to the proposing session id (and their original Workspace when scoped); sessions with other ids cannot resolve them. They persist when the same session resumes. Only pending candidates are retained: confirmed or rejected candidates disappear, while committed entries keep the confirming message as their source. Pending content is limited to 25 candidates per session and 100 in the store. The assistant must display the candidate and, for replacements, the old entry before requesting the exact command.

Search uses case-folded literal words and adjacent Chinese/Japanese/Korean characters from the memory **content**. It ranks by number of matching query terms, then an exact-phrase bonus, then the most recent verification time and id. It does not search citations, infer synonyms, or guess when to run. A query must contain 1–200 characters and 1–24 meaningful terms; `limit` must be 1–10. Invalid queries return an error. Results include only reviewed Global entries and reviewed entries in the current canonical Workspace. Other Workspaces and older `needs-review` entries are excluded; use `memory_list` to audit those older entries.

The Prompt provider is disabled by default (`promptEntries: 0`), pending the task observation in S4. If explicitly enabled, it inserts only `verified` entries, up to `promptEntries` within `promptCharacters` total characters (default 1200), marked as background information. Setting either limit to zero disables injection. Enabled injection currently orders entries by verification time, not task relevance. No automatic summarization, saving, vector search, reflection, or conflict merging occurs.

## Recovery and limits

New confirmed entries retain the direct user confirmation's session id, event sequence, and event-time Workspace. S3 replaces the exposed `memory_add` and `memory_update` tools with `memory_propose`, `memory_pending`, and `memory_decide`; existing callers must switch to the confirmed flow. Original v1 and v2 files are read without modification; a regular edit to v1 still writes v2, while the first candidate proposal writes v3 with a separate `candidates` array. Once v3 is written it stays v3 even when all candidates are resolved. Profiles running the older v1/v2-only plugin will refuse a v3 file: upgrade **every** Profile using the same DSH Home before proposing a candidate. To review an older `needs-review` fact, read it, propose a replacement using its exact id and scope, then show both versions to the user for confirmation. The repository does not perform Profile upgrades or touch actual memory data.

Malformed, unreadable, unknown-version or stale data cannot be overwritten by these tools. Restore a known good backup externally, then list before editing. Writers use the shipped `withFileLock` around read, compare and atomic replacement; cooperative processes on one host serialize. An orphaned lock with an incomplete record or a reused live PID may time out and require an operator to check for live writers before removing its `.lock` file. The atomic replacement has no `fsync`; abrupt power loss can lose the most recent write even after it reports success. External programs editing the file without this lock can race; keep other writers cooperative. An external edit made before a locked mutation is detected through the revision or validation.

Tests run using Node's test runner and only create files under the operating system's temporary directory. The package's bundled dependencies are installed in this workspace with scripts disabled before testing; neither tests nor installation should target actual memory data.
